`catalog/` holds what the Projects, Clients and Tags pages share (`docs/PRD.md` P2 to P4). `CatalogModel` loads a page's items from the account's default workspace each time the page opens, when the phone comes back online and when the app comes back to the foreground with the page open, and sends each change at once. Every create of a project, client, tag or task goes through `createOnce` in `catalog/CreateOnce.kt`, which finds the item a create with a lost answer made by reading the list again, so a retry never meets Tokkl's duplicate-name refusal (see the change queue node). `CatalogModel` is a `PageLoads`: each page's view model shares its page state with `stateInPage` from `platform/PageLoads.kt` (`whileShown`, five seconds), which calls `shown` when a screen starts reading the state (the first time, or after none read it for five seconds, as when the Pomodoro alarm or the tile's dialog covered the page), `returned` when the app comes back to the foreground through `ProcessLifecycleOwner` while a screen reads it, and `reconnected` on each network return while a screen reads it. A rotation keeps the view model and its sharing, so turning the phone sends no request. A load keeps the list and the open form or question on screen until the answer comes, so a page that shows again, after a trip to the background or from under another activity, keeps what the user had open and loads again for it; the projects page also loads the open form's tasks again. `reconnected` loads only while the page could not reach the server. What a page loaded and has open goes with its view model, the route's own, when the route leaves the back stack. `CatalogModel.close()` resets a list, which only the project form's task list does, as its form closes. `TagsViewModelTest`, `ClientsViewModelTest`, `ProjectsViewModelTest` and `TrashViewModelTest` pin that the open form or question survives the screen hidden for longer than five seconds. Each page's route composable, `ClientsPage`, `ProjectsPage` or `TagsPage` in the feature's `XEntries.kt`, takes the view model and collects its page state; `ClientsScreen`, `ProjectsScreen` and `TagsScreen` take the page state and the actions, as in `TagsScreen(page, actions)`. Each page's view model keeps its `CatalogModel` state internal and exposes one page state, `TagsPageState`, `ClientsPageState` or `ProjectsPageState`: the catalog with the offline state and the cached rows of the page's workspace, and the values the screen derives from them, `serverNeeded` and `canChange` on each, the tag `rows` and `hasNotices` on the tags page, `formOpen` on the clients page and the task list's or the catalog's `done` on the projects page. `TagsPageStateTest` pins the tags page's derived values. The projects view model opens a project's task list when its form shows a project the server sent, and closes it when the form closes. Nothing is queued: offline, or with the server out of reach, nothing changes and the page says why. After each change the server accepts, the page calls `refreshAfterChange()` on the `CacheRefresh` that `CatalogModel` takes beside the `AccountSettingsSource`, so the offline cache catches up and the picker, the history and the reports show the change. `ManagedWorkspace` takes the workspace from the stored account settings, or from `GET /api/v9/me` when the stored settings predate that field. `CatalogModel` reads through a `CatalogRepository`, which finds the workspace and loads the list. Each page's view model gets its repository from Koin (`ClientsRepository`, `ProjectsRepository`, `TasksRepository`, `TagsRepository`; the trash and the reports have `TrashRepository` and `ReportsRepository`). `TagsRepository` and `TrashRepository` are interfaces, which `ServerTagsRepository` and `ServerTrashRepository` implement, so `TagsViewModelTest` and `TrashViewModelTest` use fakes instead of a MockWebServer; the others are one class each. A server repository goes through `SignedInApi`, which fails a signed-out call with `AuthFailed` before any request, and the feature's HTTP adapter, such as `ClientsServer`. A change the server accepted still lands when the page goes, because `CatalogModel.send` runs it in `NonCancellable`.

`ServerProblem` in core:session turns an `ApiError` into what a page shows, and `problemText` words it with core:session's strings, so the timer's notices in core:timerstate say a failure in the same words. A 502, 503 or 504 counts as the server being out of reach, because a reverse proxy answers those while Tokkl is down. A 4xx whose body is a JSON string becomes `Refused` with the server's own reason, such as "Name has already been taken". `CatalogPage` is the scrolling frame with a snackbar that names the accepted change in the web app's words, such as "Created Website". `ConfirmDialog` asks before a change that touches more than the item, as the web app's `ConfirmModal` does. Its Cancel and confirm buttons stack at full width, because `AlertDialog`'s own button row put one over the other at 200% font scale.

`projects/`, `clients/` and `tags/` each hold a page's screen, model, view model, repository and server calls. Projects and clients are created, edited, archived and restored. Tags are created, renamed and deleted. core:api reads each answer into its own type, such as `WorkspaceTag` or `WorkspaceClient`, and each server class maps it to the model's types, the same the cache gives for its offline rows: `TagsServer` gives `Tag`, `ClientsServer` gives `Client` with its notes, which the cache leaves null, and `TasksServer` gives `Task`. The projects page keeps its own `ProjectDetails`, a project with its client's name, rate, currency and estimate, which the model's `Project` lacks. The pages' workspace is a `WorkspaceId`, and their ids are the model's typed ids.

A project's form holds its tasks (P5), as the web app's `ProjectTasks` does. `projects/TasksModel` and `ProjectTasks.kt` draw and run the list, and `TasksServer` calls `/api/v9/workspaces/{id}/projects/{id}/tasks`. A field adds a task while the project is active, then come the open tasks and the done ones, each part sorted as Tokkl sorts them. A tap on a task opens a form that renames it and marks it done, and Delete asks first and names the task. Names stop at 255 characters, the web app's limit, which Tokkl enforces too. Task changes follow the catalog's rules: sent at once, nothing queued, every action off while offline, and a cache refresh after each accepted change so the entry picker offers it.
