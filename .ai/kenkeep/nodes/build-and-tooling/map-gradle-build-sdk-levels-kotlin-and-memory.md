The modules are listed in `settings.gradle.kts`. `:app` is only the shell: `TokklApplication`, `MainActivity`, the startup and lifecycle observers, what spans the modules (`lifecycle/AppRefreshSteps`, what each account refresh does after its answer), the list of Koin modules in `di/AppModules.kt` and the navigation host in `navhost`. Each core module ships its own Koin module, as each feature does: `platformModule`, `sessionModule`, `trustModule`, `cacheModule` (with the queue's workers), `timerStateModule`, `timerNoticeModule` (core:timersync's second, in its `timernotice` package, with the worker that sends the notification's and the widget's timer actions) and `timerSyncModule`. The wiring that joins two components is a named class in the lower module, such as `SendOnQueue`, `QueueDrainEvents`, `SendThenRefresh` and `CapabilitiesSignOut`, so the Koin modules only construct. `AppModulesTest` fails when the app's own Koin modules define a core or feature class beyond the few that join every module's parts. What a module does at process start, on MainActivity's starts and when the user allows notifications is a class of its own that implements core:platform's `AppHook` interface, which names only those three moments, such as `RunningCheckHook` or `TimerSyncHook`, bound in the module's Koin module with `bind AppHook::class`. The app's `di/HooksModule.kt` lists every hook in the order they run, with the reason for each place, and `AppHooks` refuses a bound hook that list leaves out. `AppStartup` and `MainActivityForeground` run the list, and `AppHookOrderTest` pins it as a list of the hooks' class names, so a new step adds a hook class and a line in each. A hook that follows a flow for the whole process, such as the notifications', the widgets', the shortcuts', the phase alarm's and the running check's, collects it through core:platform's `collectDurably`, which reads the flow again after a failed read and tries a failed step again, after a wait of one second doubling up to two minutes, so a failure of the disk or the database never ends it. Koin binds every definition by its type and holds no string names. The only qualifiers left are the dispatchers', typed as `named<AppDispatcher.Main>()`, `Io` and `Default` in core:platform's `AppDispatcher.kt`. Main code takes every dispatcher from them: `io()`, `computation()` and `viewModelCoroutineScope()` read them in a Koin definition, and an Android component injects one, so no class falls back to a `Dispatchers` default. `LoadedState` and `ThemeSettingsRepository` take the context their startup load runs on, which Koin gives as `io()`. A class Koin builds takes each collaborator as a named type, such as `CacheRefresh`, `SignInStatus` or `CurrentTimerState`, not as a lambda or a method reference, and the extra types `AppModulesTest` allows in a constructor hold no function type. The core libraries stand in layers, each depending only on lower ones, as `ModuleLayersTest`'s `CORE_LAYERS` lists them. At the bottom, alone, `:core:model` (what the screens show and change, with typed ids, and the server's `Capabilities` flags). Above it, `:core:api` (the HTTP client and the API's types, whose calls take the model's ids), `:core:time` (account time and durations), `:core:ui` (the design system) and `:core:platform` (dispatchers, Koin helpers, the default network, WorkManager, receivers and the disk store interfaces). Above them `:core:session` (the token, the server and its trust, the capabilities' refresh, the account settings and their refresh, sign-out, the synced preferences, and `ServerProblem` with its words for a failed request), then `:core:cache` (the Room cache and the change queue), then `:core:timerstate` (the timer state engine, its actions and the controls, with no WorkManager and nothing a surface shows). The Pomodoro widget stays in `:feature:widget`: its receiver's class name, `com.github.e0ipso.tokkl.widget.PomodoroWidgetReceiver`, is the widget's identity on the launcher, so moving it to another package would drop every placed widget, and a package lives in one module. Then `:core:timersync` (the timer event stream, `TimerSyncService` that holds it in the background, declared in the module's own manifest, and `TimerSyncFollower`, which starts and stops both; and the timer state's Android delivery: in its `timernotice` package the expedited worker of the notification's and the widget's actions, what the timer's surfaces say when an action does not go through, `TimerFailureNotice`, which feature:notification implements with a toast, and `TimerFrame`, and in its `timersync` package the Pomodoro alarm, ring and widget redraw contracts, `PomodoroAlarmScheduler`, `PomodoroRingingPhase` and `PomodoroWidgetRedraw`, which the Pomodoro and widget features share), the parts several features show, `:core:catalog` (the catalog pages' frame), `:core:entryfields` (the entry fields editor and its picker) and `:core:trust` (the trust prompts), and `:core:navigation`, which holds the `Route` interface with Timer's and the entry form's routes, the `Navigator`, the contracts through which the features hand the host their parts, each bound only by the features that give it (`FeatureRoutes`, with which a feature declares its routes, adds its screens and names its top-level pages, `FeatureRequests`, with which it reads and opens its taps from outside the app, and `FrameContributions`, with which it adds its parts to the signed-in frame, gathered in `FeatureNavigation`), `PageBadge`, `SignInRoutes` and `TopLevelPages`. `:core:navigation` depends on `:core:model`, `:core:ui` and Navigation 3 only, with no Koin. Each module exposes with `api` only the modules whose types its consumers get through its contracts, and `ModuleLayersTest.EXPOSED` lists each such dependency with why. `:core:api` exposes `:core:model`, and of its libraries only kotlinx-serialization-core and the coroutines: OkHttp and kotlinx-serialization-json are implementation details, so no module above compiles against OkHttp, and a module that writes JSON of its own names the JSON library. `:core:session` exposes `:core:api`, `:core:model` and `:core:time`, since `Session` is the API client provider and the account settings give the account's time. `:core:cache` and `:core:timerstate` expose only `:core:model`, `:core:timersync` and `:core:trust` nothing, and `:core:entryfields` only `:core:model` and `:core:time`, so a picker brings no Room or OkHttp to its users. Every module names in its build file each module its sources use, so a module that uses `:core:timerstate` compiles against `:core:model` with it, where it used to get the cache, the session, the API, the platform and the time too. What only a module's own Koin module builds, such as `TimerSync`'s constructor and connections and the queue's delivery wiring, is internal. `:core:entryfields` and `:core:catalog` draw with `:core:ui` as an implementation detail, since none of their signatures name its types. No module outside `:core:cache` names Room, its database or a table: they read what changed through the cache's flows, such as `AccountCache.entriesOrQueueChanged`, and `PackageLayersTest.roomStaysInTheCache` checks it. The features are `:feature:signin`, `:feature:timer` (the Timer page with history, calendar, entry form and timer templates), `:feature:pomodoro`, `:feature:reports`, `:feature:projects`, `:feature:clients`, `:feature:tags`, `:feature:trash`, `:feature:settings` (with Licences), `:feature:sync`, `:feature:notification` (with the reminder), `:feature:shortcuts`, `:feature:tile` and `:feature:widget`. A feature depends on core modules only, never on another feature, names in its build file each core module its main sources use, and binds its own `xFeatureModule` Koin module, which `di/AppModules.kt` lists. A feature with a top-level page names its `TopLevelDestination` in its `FeatureRoutes.pages`: its route, label, icon, section hue, position and whether it sits on the More sheet. The app's navigation module puts every feature's pages into `TopLevelPages`, ordered by position (Timer 0, Pomodoro 10, Reports 20, Projects 30, Timer templates 40, Clients 50, Tags 60, Trash 70, Settings 80), so a new page needs no change in core or the app's bar. Each feature declares its manifest components under their full class names in its own manifest. The included build `build-logic` holds the convention plugins `tokkl.android.application`, `tokkl.android.library`, `tokkl.android.library.compose`, `tokkl.android.feature`, `tokkl.android.feature.screen` and `tokkl.jvm.library`, which set compileSdk, Build-Tools, minSdk, the app's targetSdk, Java 17, Compose, detekt and the lint input described below; the feature plugin also sets the namespace, Koin, the JUnit and coroutine test libraries and the instrumented test setup, and the screen feature plugin adds Compose with Material 3, Compose UI, the view model's Compose integration and Koin's. The ten features with routes and view models apply the screen plugin; `:feature:notification`, `:feature:tile` and `:feature:widget` apply the feature plugin with `tokkl.android.library.compose` and name the Compose libraries they draw with, and `:feature:shortcuts`, which draws nothing, applies the feature plugin alone. Each feature's build file names its core modules. `app/build.gradle.kts` keeps the version, release signing, R8, `dependenciesInfo` and `checkDeniedDependencies`. `:core:model`, `:core:api` and `:core:time` have no Android code and build with `tokkl.jvm.library`: Kotlin/JVM at Java 17, Android lint through `com.android.lint`, and detekt. They compile against the JDK, not android.jar, and Android lint has no minSdk for a Kotlin/JVM module, so its NewApi check stays silent there: on 2026-11-08 a call to `java.util.HexFormat` (API 34) passed lint in core:api and core:time, also with `checkDependencies` on the app, while the same call in core:platform failed. So `tokkl.jvm.library` also applies Animal Sniffer (`ru.vyarus.animalsniffer`, MIT) with the API 31 signature of gummy-bears (`com.toasttab.android:gummy-bears-api-31`, Apache-2.0): `animalsnifferMain` checks the main classes, `check` and `lint` run it, and a call that Android 12 lacks fails the build. Their unit tests are `test`, not `testDebugUnitTest`, and their lint reports are `build/reports/lint-results.*`. Every other module is an Android library, whose Kotlin compiles against android.jar. Kotlin packages kept their names. Each module's Android namespace is `com.github.e0ipso.tokkl.core.<name>` or `com.github.e0ipso.tokkl.feature.<name>`, so code reads that module's resources through its R class, such as `com.github.e0ipso.tokkl.core.ui.R`. A resource lives in the module whose code reads it. One that several modules read and no shared code does, such as the Pomodoro, date, template and timer control strings, sits in core:ui. `PackageLayersTest` and `ModuleLayersTest` in `app/src/test` keep packages and modules in layers, and `ModuleLayersTest` also fails on a cycle between modules. Fakes that several modules' tests share are test fixtures (`src/testFixtures`) of core:api (through `java-test-fixtures`), core:ui, core:platform (`InMemoryValueStore`, and `MainDispatcherRule` for coroutine tests in virtual time), core:session (`CountingRefresh`, `capabilitiesOf`, `accountSettingsOf` and `accountSettingsIn`) and core:timerstate (`ServerTimerStates` and `FixedTimerState`). The instrumented tests that need the app, MainActivity, the test server, the session rule, Koin or the screenshots stay in `app/src/androidTest`. A test that draws one screen's composables, or reads one store, and needs none of that lives in its feature's `src/androidTest` and runs in that feature's own test APK, under the same runner, orchestrator and targetSdk, so it reads the feature's `internal` declarations. What the app's tests read of a feature must be public, since Kotlin has no package-private. A pure unit the app's tests use, such as an intent builder, a formatter or a notification's `build`, is public with KDoc and no `@VisibleForTesting`. A name that is a contract with stored data or the platform, such as a file name, a Keystore alias or a notification channel id, stays private, and the test spells the literal out, so a rename fails it. `@VisibleForTesting` stays only where a test in another module needs a member that production would keep narrower: running state the device tests observe, such as the ringing service's player, the stepper's test tags, and `SurfaceTap.Request`'s constructor, with which other modules' JVM tests stand in for a tap. Each says why in its comment or KDoc. `:core:testing` holds what both kinds share: `AccessibilityTestRunner`, `StepAwareShardingFilter`, the accessibility compose rules, `DeviceShell`, `SystemFontScale`, `SystemDisplaySize` and the Pomodoro length card matchers. Only androidTest source sets depend on it, so the architecture tests leave it out of the module graph.

After code moves between modules, Kotlin's incremental compilation can skip a file that now reads another module's `internal` declaration, and the build passes. On 2026-11-06 it hid such an error in the app's unit tests. Check a move with `-Pkotlin.incremental=false` and `--rerun` after each compile task.

`minSdk` is 31, Android 12, since the owner's decision of 2026-10-19. `TARGET_SDK` in build-logic's `AndroidConventions.kt` holds the targetSdk for the app and for the feature modules' test APKs. `compileSdk` is 37 because Compose UI 1.12 declares `minCompileSdk` 37 in its AAR metadata, and a lower value fails AGP's AAR metadata check. `targetSdk` stays at 36, the API level of the emulator `tokkl-api36`, so lint reports `OldTargetApi` and the project accepts that warning. Raise `targetSdk` together with the emulator image, not to silence lint.

AGP 9 compiles Kotlin itself and brings Kotlin Gradle plugin 2.2.10. The `kotlin-compose` plugin in `gradle/libs.versions.toml` depends on the Kotlin Gradle plugin of the catalog's `kotlin` version (2.4.21) and raises it, so the root `build.gradle.kts` has no Kotlin classpath entry. Change the Kotlin version in that one catalog entry.

`gradle.properties` allows for the other services on this machine. `org.gradle.jvmargs` caps the daemon heap at `-Xmx2g` and metaspace at 768m, and `kotlin.compiler.execution.strategy=in-process` compiles Kotlin inside the Gradle daemon instead of a second long-lived Kotlin daemon.

`org.gradle.caching=true` turns on Gradle's local build cache in `~/.gradle/caches/build-cache-1`, which every checkout and worktree on the machine shares. Drain sittings each build in a new worktree from the same commit. On a fresh copy of 62beaf3, `assembleDebug assembleDebugAndroidTest testDebugUnitTest` took 1m 57s on an empty cache and 13s on a warm one, with every KSP, Kotlin compile and dex task taken from the cache. `checkDeniedDependencies` declares no outputs, so it runs on every `check`, and `connectedDebugAndroidTest` never uses the cache. `scripts/reproducible-release.sh` builds with `--no-build-cache`, so both of its builds compile from clean, as F-Droid's does.

Lint's analysis cannot be relocated between checkouts. It stores this module's files relative to path variables but files outside it, such as `gradle/libs.versions.toml`, by absolute path, and AGP 9.4.1 passes lint no `--path-variables`. Taken from the shared cache, one worktree's analysis made another worktree's lint report cite the first worktree's files. So the convention plugins in `build-logic` add the checkout's absolute path as an input of every lint analysis task in every module, and the analysis comes from the cache only for the checkout that ran it. They find those tasks by name, `lintAnalyze<Variant>` and `lintVitalAnalyze<Variant>`, because their class, `AndroidLintAnalysisTask`, is internal to AGP. With AGP 9.4.1 the names matched the same 167 tasks as the class on 2026-11-08; check that again when AGP changes. Remove that input only once AGP can relocate lint's analysis.

`org.gradle.configuration-cache=true` turns on Gradle's configuration cache. Every usual command, `connectedDebugAndroidTest` through the script included, reuses its entry on a second run: AGP reads the instrumentation runner arguments only when the tests run, so the new ports, fingerprints and filter file of each script run do not invalidate it.

Room 2.8.5 generates its code through KSP 2.3.12, and the Room Gradle plugin writes each database version's schema to `core/cache/schemas/`. Those JSON files are tracked. Room's auto-migrations read them, so commit the new schema file with every version bump of `CacheDatabase`.

The wrapper is Gradle 9.8.2. `distributionSha256Sum` in `gradle/wrapper/gradle-wrapper.properties` pins its checksum, so change the sum whenever `distributionUrl` changes.

`.gitattributes` keeps `gradlew` at LF and `*.bat` at CRLF, as Gradle's init template does. A `gradlew` with CRLF does not run on Linux, whatever `core.autocrlf` says.
