`TokklNavHost` keeps a Navigation 3 back stack of `Route`s, saved with their serializers, so it survives configuration changes and process death. `Route` is an open interface in `:core:navigation`, which declares only `Route.Timer`, at the bottom of every signed-in stack, and `Route.Entry`, the entry form that the timer and sync features both open. Each feature declares its other routes as `@Serializable` objects or classes, such as `ClientsRoute`, `FullscreenTimerRoute` or `SignInRoute`, and registers them in `FeatureRoutes.registerRoutes`. The host saves the stack with `NavBackStackSerializer(PolymorphicSerializer(Route::class))` and a `SavedStateConfiguration` whose serializers module `routeSerializers` builds from every feature's `FeatureRoutes`, so a feature's new route needs no change in core. `SavedBackStackTest` round-trips a stack of every route through that serializer; a route a feature forgets to register fails it. `FeatureRoutesTest` assembles the navigation from the app's Koin graph and fails when a route a feature registers, or names as a top-level page, has no entry or no serializer. The routes that moved to their features on 2026-11-08 keep, with `@SerialName`, the serial names they had in the sealed `Route` before (`com.github.e0ipso.tokkl.navigation.Route.Clients` and so on), so a stack saved by an earlier version reads as before; `SavedBackStackTest` checks those names. Their `contentKey`s, which are their `toString()`, changed with their class names. A route marks itself `focused`, as the fullscreen timer does, to hide the bar, and the entry form above it hides it too. Routes carry ids, never entries: the entry form's `EntryOpening` holds the model's `EntryId` and `WorkspaceId`, which serialize as their numbers. `EntryFormOpenings` keeps in memory the copy of an entry the cache lacks, and its `take` gives every route its opening, so a form restored in a new process opens on its route and its own saved state. `:core:navigation` depends on `:core:model`, `:core:ui` and Navigation 3 only: no session, no cache and no Koin. No feature names another's screens: each feature with a screen binds a `FeatureRoutes` in its Koin module that names its top-level pages, registers its routes and adds their entries, and the host builds its entry provider from every one Koin holds. The contract has no default members, so a feature without a page says so with an empty `pages`. The app's navigation module gathers every feature's `FeatureRoutes`, `FeatureRequests` and `FrameContributions` into one `FeatureNavigation`, which MainActivity injects and hands the host. A screen opens another feature's screen through the `Navigator`, by its route. Each entry's view models live in a store that Navigation 3's `ViewModelStoreNavEntryDecorator` clears when the entry leaves the stack, and the view models several screens share live in the session's store, under a key no route has, of the same `ViewModelStoreProvider`. `NavigationStores`, a view model of MainActivity, holds that provider, so both outlive a configuration change, and drops it after every sign-out, also one that finished while MainActivity was made again. Lifecycle's `rememberViewModelStoreProvider` would not clear its stores in that case, which is why the host keeps its own. The host starts at sign-in until a server and token are stored, and at the Timer page after that. The sign-in feature binds `SignInRoutes`, which says whether somebody is signed in (it reads the stores on the IO dispatcher), gives the sign-in route and tells one apart, so the host names no `SignInRoute`. A back stack restored from saved state can outlive its session, after a sign-out that finished in the background or a token that no longer decrypts, so when its top is not sign-in the host checks `isSignedIn()` once and goes to sign-in if nobody is signed in. The taps from outside the app reach MainActivity as intents. Each feature that owns the page a tap opens declares the tap as a `@Serializable` `NavigationRequest` and binds a `FeatureRequests`, such as `TimerRequests`, `ReportsRequests` or `PomodoroRequests`, that registers its serializer (`registerRequests`), reads it from an intent's action and extras (`readLinks`, through a `LinkIntent` with no Android in it), names the extras it reads (`linkExtras`) and opens it (`OpenRequest`); a feature that no tap opens binds none: Timer opens the Timer widget's tap and the reminder's, Reports the widget's day report, and Pomodoro its widget's tap and a session notification's tap for its account and phase. The widget and the reminder write those extras, and each feature reads the same string; `DeepLinksTest` checks both sides agree over the app's graph. `navhost/DeepLinks` asks every feature, and `takeDeepLinks` removes the extras so a rotation opens nothing again. What still waits sits in `NavigationRequests`, MainActivity's view model, which keeps it in its `SavedStateHandle` with the features' request serializers, so it outlives a configuration change and the process; a request an older version saved and this one no longer knows waits no more. One request of each class waits at a time. Above every signed-in screen the host shows the session's trust prompt, or after a cancel the notice that reopens it.
