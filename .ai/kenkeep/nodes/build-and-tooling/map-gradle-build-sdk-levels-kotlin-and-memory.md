The modules are listed in `settings.gradle.kts`. `:app` is only the shell: `TokklApplication`, `MainActivity`, the startup and lifecycle observers, the Koin assembly in `di` (with the account refresh's steps in `AccountModule`) and the navigation host in `navhost`. What a module does at process start, on MainActivity's starts and when the user allows notifications is an `AppHook` it binds in its own Koin module under a name; `AppStartup` and `MainActivityForeground` collect them with `getAll()` and run them in `AppHookOrder`, so a new step adds a hook and an entry there, not a constructor parameter. The core libraries stand in layers, each depending only on lower ones, as `ModuleLayersTest`'s `CORE_LAYERS` lists them. At the bottom, `:core:model` (what the screens show and change, with typed ids), `:core:api` (the HTTP client and the API's types), `:core:time` (account time and durations), `:core:ui` (the design system) and `:core:platform` (dispatchers, Koin helpers, the default network, WorkManager, receivers and the disk store interfaces). Above them `:core:session` (the token, the server and its trust, the capabilities, the account settings and their refresh, sign-out and the synced preferences), then `:core:cache` (the Room cache and the change queue), then `:core:timerstate` (the timer state, its actions and the Pomodoro contracts that the Pomodoro and widget features share). Then `:core:timersync` (the timer event stream, `TimerSyncService` that holds it in the background, declared in the module's own manifest, and `TimerSyncFollower`, which starts and stops both), the parts several features show, `:core:catalog` (the catalog pages' frame and the server problems), `:core:entryfields` (the entry fields editor and its picker) and `:core:trust` (the trust prompts), and `:core:navigation`, which holds the `Route` interface with Timer's and the entry form's routes, the `Navigator`, the `FeatureEntries` interface through which each feature declares its routes, adds its screens and names its top-level pages, and `TopLevelPages`. `:core:navigation` depends on `:core:model`, `:core:ui` and Navigation 3 only, with no Koin. Last comes `:core:timernotice`, the timer action notices, which read as the catalog's problems. Each module exposes with `api` the modules whose types its public API carries, so `:core:cache` exposes `:core:session`, which exposes `:core:model`, `:core:api`, `:core:time` and `:core:platform`. The features are `:feature:signin`, `:feature:timer` (the Timer page with history, calendar, entry form and timer templates), `:feature:pomodoro`, `:feature:reports`, `:feature:projects`, `:feature:clients`, `:feature:tags`, `:feature:trash`, `:feature:settings` (with Licences), `:feature:sync`, `:feature:notification` (with the reminder), `:feature:shortcuts`, `:feature:tile` and `:feature:widget`. A feature depends on core modules only, never on another feature, names in its build file each core module its main sources use, and binds its own `xFeatureModule` Koin module, which `di/AppModules.kt` lists. A feature with a top-level page names its `TopLevelDestination` in its `FeatureEntries.pages`: its route, label, icon, section hue, position and whether it sits on the More sheet. The app's navigation module puts every feature's pages into `TopLevelPages`, ordered by position (Timer 0, Pomodoro 10, Reports 20, Projects 30, Timer templates 40, Clients 50, Tags 60, Trash 70, Settings 80), so a new page needs no change in core or the app's bar. Each feature declares its manifest components under their full class names in its own manifest. The included build `build-logic` holds the convention plugins `tokkl.android.application`, `tokkl.android.library`, `tokkl.android.library.compose`, `tokkl.android.feature` and `tokkl.jvm.library`, which set compileSdk, Build-Tools, minSdk, the app's targetSdk, Java 17, Compose, detekt and the lint input described below; the feature plugin also sets the namespace, the Compose, lifecycle, Koin and JUnit libraries and the instrumented test setup, and each feature's build file names its core modules. `app/build.gradle.kts` keeps the version, release signing, R8, `dependenciesInfo` and `checkDeniedDependencies`. `:core:model`, `:core:api` and `:core:time` have no Android code and build with `tokkl.jvm.library`: Kotlin/JVM at Java 17, Android lint through `com.android.lint`, and detekt. They compile against the JDK, not android.jar, and Android lint has no minSdk for a Kotlin/JVM module, so its NewApi check stays silent there: on 2026-11-08 a call to `java.util.HexFormat` (API 34) passed lint in core:api and core:time, also with `checkDependencies` on the app, while the same call in core:platform failed. So `tokkl.jvm.library` also applies Animal Sniffer (`ru.vyarus.animalsniffer`, MIT) with the API 31 signature of gummy-bears (`com.toasttab.android:gummy-bears-api-31`, Apache-2.0): `animalsnifferMain` checks the main classes, `check` and `lint` run it, and a call that Android 12 lacks fails the build. Their unit tests are `test`, not `testDebugUnitTest`, and their lint reports are `build/reports/lint-results.*`. Every other module is an Android library, whose Kotlin compiles against android.jar. Kotlin packages kept their names. Each module's Android namespace is `com.github.e0ipso.tokkl.core.<name>` or `com.github.e0ipso.tokkl.feature.<name>`, so code reads that module's resources through its R class, such as `com.github.e0ipso.tokkl.core.ui.R`. A resource lives in the module whose code reads it. One that several modules read and no shared code does, such as the Pomodoro, date, template and timer control strings, sits in core:ui. `PackageLayersTest` and `ModuleLayersTest` in `app/src/test` keep packages and modules in layers, and `ModuleLayersTest` also fails on a cycle between modules. Fakes that several modules' tests share are test fixtures (`src/testFixtures`) of core:api (through `java-test-fixtures`), core:ui, core:platform (`InMemoryValueStore`, and `MainDispatcherRule` for coroutine tests in virtual time) and core:timerstate (`ServerTimerStates`). The instrumented tests that need the app, MainActivity, the test server, the session rule, Koin or the screenshots stay in `app/src/androidTest`. A test that draws one screen's composables, or reads one store, and needs none of that lives in its feature's `src/androidTest` and runs in that feature's own test APK, under the same runner, orchestrator and targetSdk, so it reads the feature's `internal` declarations. What the app's tests read of a feature must be public, since Kotlin has no package-private. A pure unit the app's tests use, such as an intent builder, a formatter or a notification's `build`, is public with KDoc and no `@VisibleForTesting`. A name that is a contract with stored data or the platform, such as a file name, a Keystore alias or a notification channel id, stays private, and the test spells the literal out, so a rename fails it. `@VisibleForTesting` stays only where a test in another module needs a member that production would keep narrower: running state the device tests observe, such as the ringing service's player, the stepper's test tags, and `SurfaceTap.Request`'s constructor, with which other modules' JVM tests stand in for a tap. Each says why in its comment or KDoc. `:core:testing` holds what both kinds share: `AccessibilityTestRunner`, `StepAwareShardingFilter`, the accessibility compose rules, `DeviceShell`, `SystemFontScale`, `SystemDisplaySize` and the Pomodoro length card matchers. Only androidTest source sets depend on it, so the architecture tests leave it out of the module graph.

After code moves between modules, Kotlin's incremental compilation can skip a file that now reads another module's `internal` declaration, and the build passes. On 2026-11-06 it hid such an error in the app's unit tests. Check a move with `-Pkotlin.incremental=false` and `--rerun` after each compile task.

`minSdk` is 31, Android 12, since the owner's decision of 2026-10-19. `TARGET_SDK` in build-logic's `AndroidConventions.kt` holds the targetSdk for the app and for the feature modules' test APKs. `compileSdk` is 37 because Compose UI 1.12 declares `minCompileSdk` 37 in its AAR metadata, and a lower value fails AGP's AAR metadata check. `targetSdk` stays at 36, the API level of the emulator `tokkl-api36`, so lint reports `OldTargetApi` and the project accepts that warning. Raise `targetSdk` together with the emulator image, not to silence lint.

AGP 9 compiles Kotlin itself and brings Kotlin Gradle plugin 2.2.10. The `kotlin-compose` plugin in `gradle/libs.versions.toml` depends on the Kotlin Gradle plugin of the catalog's `kotlin` version (2.4.21) and raises it, so the root `build.gradle.kts` has no Kotlin classpath entry. Change the Kotlin version in that one catalog entry.

`gradle.properties` allows for the other services on this machine. `org.gradle.jvmargs` caps the daemon heap at `-Xmx2g` and metaspace at 768m, and `kotlin.compiler.execution.strategy=in-process` compiles Kotlin inside the Gradle daemon instead of a second long-lived Kotlin daemon.

`org.gradle.caching=true` turns on Gradle's local build cache in `~/.gradle/caches/build-cache-1`, which every checkout and worktree on the machine shares. Drain sittings each build in a new worktree from the same commit. On a fresh copy of 62beaf3, `assembleDebug assembleDebugAndroidTest testDebugUnitTest` took 1m 57s on an empty cache and 13s on a warm one, with every KSP, Kotlin compile and dex task taken from the cache. `checkDeniedDependencies` declares no outputs, so it runs on every `check`, and `connectedDebugAndroidTest` never uses the cache. `scripts/reproducible-release.sh` builds with `--no-build-cache`, so both of its builds compile from clean, as F-Droid's does.

Lint's analysis cannot be relocated between checkouts. It stores this module's files relative to path variables but files outside it, such as `gradle/libs.versions.toml`, by absolute path, and AGP 9.4.1 passes lint no `--path-variables`. Taken from the shared cache, one worktree's analysis made another worktree's lint report cite the first worktree's files. So the convention plugins in `build-logic` add the checkout's absolute path as an input of every lint analysis task in every module, and the analysis comes from the cache only for the checkout that ran it. They find those tasks by name, `lintAnalyze<Variant>` and `lintVitalAnalyze<Variant>`, because their class, `AndroidLintAnalysisTask`, is internal to AGP. With AGP 9.4.1 the names matched the same 167 tasks as the class on 2026-11-08; check that again when AGP changes. Remove that input only once AGP can relocate lint's analysis.

`org.gradle.configuration-cache=true` turns on Gradle's configuration cache. Every usual command, `connectedDebugAndroidTest` through the script included, reuses its entry on a second run: AGP reads the instrumentation runner arguments only when the tests run, so the new ports, fingerprints and filter file of each script run do not invalidate it.

Room 2.8.5 generates its code through KSP 2.3.12, and the Room Gradle plugin writes each database version's schema to `core/cache/schemas/`. Those JSON files are tracked. Room's auto-migrations read them, so commit the new schema file with every version bump of `CacheDatabase`.

The wrapper is Gradle 9.8.2. `distributionSha256Sum` in `gradle/wrapper/gradle-wrapper.properties` pins its checksum, so change the sum whenever `distributionUrl` changes.

`.gitattributes` keeps `gradlew` at LF and `*.bat` at CRLF, as Gradle's init template does. A `gradlew` with CRLF does not run on Linux, whatever `core.autocrlf` says.
