The core libraries stand in layers, each depending only on lower ones, as `ModuleLayersTest`'s `CORE_LAYERS` lists them. At the bottom, alone, `:core:model` (what the screens show and change, with typed ids, and the server's `Capabilities` flags). Above it, `:core:api` (the HTTP client and the API's types, whose calls take the model's ids), `:core:time` (account time and durations), `:core:ui` (the design system) and `:core:platform` (dispatchers, Koin helpers, the default network, WorkManager, receivers and the disk store interfaces). Above them `:core:session` (the token, the server and its trust, the capabilities' refresh, the account settings and their refresh, sign-out, the synced preferences, and `ServerProblem` with its words for a failed request), then `:core:cache` (the Room cache and the change queue), then `:core:timerstate` (the timer state engine, its actions and the controls, with no WorkManager and nothing a surface shows). The Pomodoro widget stays in `:feature:widget`: its receiver's class name, `com.github.e0ipso.tokkl.widget.PomodoroWidgetReceiver`, is the widget's identity on the launcher, so moving it to another package would drop every placed widget, and a package lives in one module. Then `:core:timersync` (the timer event stream, `TimerSyncService` that holds it in the background, declared in the module's own manifest, and `TimerSyncFollower`, which starts and stops both; and the timer state's Android delivery: in its `timernotice` package the expedited worker of the notification's and the widget's actions, what the timer's surfaces say when an action does not go through, `TimerFailureNotice`, which feature:notification implements with a toast, and `TimerFrame`, and in its `timersync` package the Pomodoro alarm, ring and widget redraw contracts, `PomodoroAlarmScheduler`, `PomodoroRingingPhase` and `PomodoroWidgetRedraw`, which the Pomodoro and widget features share), the parts several features show, `:core:catalog` (the catalog pages' frame), `:core:entryfields` (the entry fields editor and its picker) and `:core:trust` (the trust prompts), and `:core:navigation`, which holds the `Route` interface with Timer's and the entry form's routes, the `Navigator`, the contracts through which the features hand the host their parts, each bound only by the features that give it (`FeatureRoutes`, with which a feature declares its routes, adds its screens and names its top-level pages, `FeatureRequests`, with which it reads and opens its taps from outside the app, and `FrameContributions`, with which it adds its parts to the signed-in frame, gathered in `FeatureNavigation`), `PageBadge`, `SignInRoutes` and `TopLevelPages`. `:core:navigation` depends on `:core:model`, `:core:ui` and Navigation 3 only, with no Koin. Each module exposes with `api` only the modules whose types its consumers get through its contracts, and `ModuleLayersTest.EXPOSED` lists each such dependency with why. `:core:api` exposes `:core:model`, and of its libraries only kotlinx-serialization-core and the coroutines: OkHttp and kotlinx-serialization-json are implementation details, so no module above compiles against OkHttp, and a module that writes JSON of its own names the JSON library. `:core:session` exposes `:core:api`, `:core:model` and `:core:time`, since `Session` is the API client provider and the account settings give the account's time. `:core:cache` and `:core:timerstate` expose only `:core:model`, `:core:timersync` and `:core:trust` nothing, and `:core:entryfields` only `:core:model` and `:core:time`, so a picker brings no Room or OkHttp to its users. Every module names in its build file each module its sources use, so a module that uses `:core:timerstate` compiles against `:core:model` with it, where it used to get the cache, the session, the API, the platform and the time too. What only a module's own Koin module builds, such as `TimerSync`'s constructor and connections and the queue's delivery wiring, is internal. `:core:entryfields` and `:core:catalog` draw with `:core:ui` as an implementation detail, since none of their signatures name its types. No module outside `:core:cache` names Room, its database or a table: they read what changed through the cache's flows, such as `AccountCache.entriesOrQueueChanged`, and `PackageLayersTest.roomStaysInTheCache` checks it. The features are `:feature:signin`, `:feature:timer` (the Timer page with history, calendar, entry form and timer templates), `:feature:pomodoro`, `:feature:reports`, `:feature:projects`, `:feature:clients`, `:feature:tags`, `:feature:trash`, `:feature:settings` (with Licences), `:feature:sync`, `:feature:notification` (with the reminder), `:feature:shortcuts`, `:feature:tile` and `:feature:widget`. A feature depends on core modules only, never on another feature, names in its build file each core module its main sources use, and binds its own `xFeatureModule` Koin module, which `di/AppModules.kt` lists. A feature with a top-level page names its `TopLevelDestination` in its `FeatureRoutes.pages`: its route, label, icon, section hue, position and whether it sits on the More sheet. The app's navigation module puts every feature's pages into `TopLevelPages`, ordered by position (Timer 0, Pomodoro 10, Reports 20, Projects 30, Timer templates 40, Clients 50, Tags 60, Trash 70, Settings 80), so a new page needs no change in core or the app's bar. Each feature declares its manifest components under their full class names in its own manifest.
