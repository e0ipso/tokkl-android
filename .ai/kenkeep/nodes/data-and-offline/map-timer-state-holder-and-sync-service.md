`timerstate/` holds the Tokkl server's timer state: the running entry, the pause chain and the Pomodoro session (`docs/PRD.md` T1, W2 to W10, section 6.3). The phone applies no phase or pause rule. `TimerStateSource` is the one holder per account. `accept` keeps the newest revision and drops a lower one, records when it arrived, so the clock offset is `server_time` minus that moment, and saves it through `TimerStateStore`. The store is a private preferences file, kept out of backups, holding no credential, so alarms, notifications and the widget act on it after process death without a request. It also holds the entry id of the last too-short pomodoro whose notice was shown. `accept` also writes the state's `running_entry` to the cache through `CurrentEntryCache`, the reconciliation `RunningCheck` uses, so queued starts, stops and edits keep showing until the server has them. Answers to `GET /api/app/timer`, to actions (409 refusals included) and stream events all enter through `accept`. The source stores the server's `TimerState` as it came and publishes it as a `HeldTimerState` in the model's types (`PauseChain`, `PomodoroSession`, `DiscardedPomodoro`), which `TimerState.held` in `timerstate/TimerStateMapping.kt` maps, so no feature reads a timer wire type. `AccountTimerStates` holds one source per account context of `session/CurrentAccount`, made on first use: the first of the process from the stored state, each later one from nothing. Sign-in calls `clearForSignIn` (retire the source, clear its store and the remembered Start fields) and then `CurrentAccount.begin`, before it stores the session, also when signing in again over a refused token. Only `AccountTimerStates` holds a source, and only it retires one. Readers take the read-only `CurrentTimerState` (the held state now, the account name and the controls) or its flows, `held`, `session`, `discardNotice` and `controls`; `withHeld` gives the account name and the held state together under the holder's lock. What feeds the state, `TimerActions`, the event stream and the account refresh's probe, takes a `TimerStateIntake`, which has only `begin` and `accept`, through `TimerStateIntakes.intake()`, once per request or stream. `AccountTimerStates` is the one class every timer surface reads: it holds the source per account and gives the held state and session for the alarm and the widget, the too-short pomodoro notice, and the controls that put the cache's running entry and the pause chain together. Sign-out retires the source in its `RETIRE_STATE` phase, before it clears the cache and the store, so a late answer for the old account changes nothing.

`TimerActions` sends the six actions as `POST /api/app/timer/pause`, `/resume`, `/discard` and `/api/app/pomodoro`, `/next`, `/end`, through `TokklApi.timer`, whose actions use `sendRefusable`, which reads a 409 body as a timer state too. They run in the application's scope, so an action reaches the server and its answer the holder also when the surface that sent it goes; `read()` runs in the caller's coroutine and stops with it. They are never queued and never resent: a lost answer shows up on the next read or event. Offline gives `TimerActionResult.Offline` and changes nothing; a 409 gives `Refused` and the holder takes the server's state. Resume, Discard, Next phase and End send the revision the control was drawn at, and `TimerTarget` also carries an account name, so a tap on an old notification or an old account's widget sends nothing. `SurfaceTap` and `TimerFailureNotice` serve the notification, widget, tile and reminder. `TimerActionResult` carries no text: core:timerstate's `timernotice` package holds the refusal and offline strings, `timerNoticeText` words each outcome, and `TimerFailureNotice` is the interface a surface calls when an action fails. core:timerstate shows nothing itself. feature:notification binds `ToastTimerFailureNotice`, which shows the toast on the main thread, and the surfaces take the notice from Koin. `SessionLengths` checks the ranges the server enforces (work 1 to 180, rests 1 to 60, long rest every 1 to 12), because the server answers 400 outside them. Start, Stop and edits of the running entry stay on the change queue.

The stream, its service and the follower sit in `:core:timersync` (package `timersync/`), above core:timerstate. `TimerSyncService` is a `specialUse` foreground service, declared with the manifest subtype property in that module's own manifest, with a silent low-importance notification on the `timer_sync` channel and no wake lock. `stopWithTask` is false. `onStartCommand` promotes before anything else and catches `ServiceStartNotAllowedException`, then stops itself; the next app open starts it. No static field holds the service. The follower holds the number of the instance that runs in the foreground (`runningService`), which the service sets on its first promotion and clears in `onDestroy`; the device tests wait on it. A stop goes through `TimerSyncFollower.stopService`, a request on a flow that the running service collects on the main thread, where it calls `stopSelf` with its latest start id, so a newer start that is still on its way promotes and decides for itself. A request made while no service runs reaches no later one. An intent action would not do: the stop would take a start id of its own and stop the service over a start sent before it. `TimerSyncFollowerTest` pins the follower's side. `TimerSync` owns the one stream. Its state changes one task at a time, in call order, on `Dispatchers.Default.limitedParallelism(1)`, so it has no lock: every method, the stream's callbacks on OkHttp threads included, hands its work to that scope and returns at once. The watchdog and the reconnects are delays in the same scope, timed by a `MonotonicClock`, which Koin binds to `ElapsedRealtimeClock` over `SystemClock.elapsedRealtime`, which counts deep sleep. `stop()` returns its job, which sign-out's step joins. `TimerEventStream` parses `GET /api/app/timer/events` by hand, a `timer` event is a state, and the 25 s `keep-alive` is an event with an empty `data:` line that only feeds the watchdog. The watchdog closes a stream silent for 60 s, reconnects wait 1 s and double up to 120 s, a stream open for 60 s resets the count, and the default network's changes, which the service collects from `DefaultNetwork` while it runs, reconnect at once. A 401 or 403 ends the stream for that account. `TimerSync` reports each end no reconnect fixes, refused or signed out, on its `terminations` flow, and `TimerSyncFollower` collects it through `collectDurably`: a refusal for the account signed in now pauses the queue through `SignInRefusal` (`PauseQueueOnRefusal` calls `ChangeSender.signInRefused()`), and either end stops the service. `TimerEventConnections` only opens the calls, so nothing below the follower holds the follower. `TimerSyncFollower.follow` decides: it runs the service only while the stream is wanted (the `timerState` capability, no refused credential, signed in), and holds the stream only for the service instance that runs now. The app open, each account refresh, sign-in and the boot and update receiver call it.

A v9 edit of the running entry moves the server's revision, the phone's own included, so a native surface tapped before the stream delivers the new state can get a 409. The Pomodoro page's `PomodoroSessionEdits`, which holds the page's session commands and the open pomodoro's edits, sends the queue and reads the revision first. `docs/PRD.md` section 6.4 lists the platform limits measured on API 36; nothing was measured on API 31. The ringing service stays a separate `mediaPlayback` service (see the alarms node).
